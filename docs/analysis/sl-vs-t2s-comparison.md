# セマンティックレイヤー vs Text-to-SQL：5-4 のまとめ（下書き）

数え方の罠は、定義に書いて強制すれば、LLM の知識に頼らずに防げる。ただし効いたのは書いた定義で、MetricFlow という道具は、書き方の難しさで足を引っ張った。定義に書けない罠（通貨、空の結果の意味）は、SL の仕組みでは防げなかった。

- **SL**（セマンティックレイヤー）：指標の定義（何をどう数えるか）を1か所に書いておき、LLM には指標の名前を選ばせて集計する層。ここでは MetricFlow（`mf query` で指標を問い合わせる道具）を使った
- **T2S**（Text-to-SQL）：LLM に表の構造を見せ、SQL を直接書かせるやり方
- 材料はすべて `docs/analysis/5-4/` の中にある。数字は run_002 のもの（run_001 のときは、そう書く）

## まとめ（shuhei、2026-10-30。run_002・gpt-oss:120b の結果から）

数え方が決まっている数字は SL に任せ、それ以外は T2S に回す。
SL は、定義に書いた数え方は守った。T2S は、値だけ合って数え方が違う答えを9本出し、見た目では気づけなかった。
ただし SL は書き方が難しく、本命の罠（2月の売上）ではエラーで T2S に負けた。
定義に書いていない所（円とドルの混在、空の結果の意味、切り口の選び方）では、SL も黙って間違えた（SL の×14本のうち10本）。
そこは、どちらを使っても人が確かめる。

## 1. 何を比べたか

- **問**：架空の messaging SaaS のデータに、汚れを意図的に仕込んだ DWH に対する13問（[questions.md](5-4/questions.md)）。4つの型に分けた
  - A 対照（罠のない問）、B SL が防ぐ罠（数え方、多重計上、孤児）、C SL でも防げない罠（通貨、未締め）、D 定義の外（SL の語彙にないことを聞く）
  - **孤児**：アカウントの表に無いアカウントの行。結合のしかたによって消える
- **正解**：人が確定した値（[answer_queries.sql](5-4/answer_queries.sql)）
  - Claude Code が書いた answer_queries.sql の結果が、下書きの [reference_queries.sql](5-4/reference_queries.sql) と13問とも一致し、人が承認したもの（questions.md）
  - A1・A3・B2〜B5・C1・C2 は、`mf query` の結果とも一致している（questions.md の「SL の上限」）。D2・D5 には、MetricFlow で突き合わせる道が無い（mf がエラーで止まる）
- **3つの組**（[run_002/conditions.md](5-4/run_002/conditions.md)）
  - `t2s`：表の列名と型だけを渡す
  - `t2s_desc`：上に、SL と同じ指標の説明文を足す
  - `sl`：指標の説明文と、使える切り口（ディメンション）と、`mf query` の書き方を渡す
- **回数**：3組 × 13問 × 3回 ＝ 117本
- **モデル**：gpt-oss:120b（Ollama の ID `714d86958b6e`）。温度（temperature）はモデルの既定値の 1。同じ指示文でも答えは揺れる
- **流れ**：LLM がクエリを書く → ハーネス（問題を渡して答えを記録する仕組み）が実行する → エラーなら1回だけ書き直させる → 結果を見せて日本語で答えさせる
- **データの版**：`data_generation/output.sha256` と CSV が4本とも一致。実行の前と後で照合した
- **実行の日時**：2026-10-29 15:26〜15:54（JST）
- **採点**：軸1「数字は正しいか」と軸2「定義の外や意味のない数字だと分かる答え方をしたか」。SL が語彙の外だと断ったら、軸1 は「答えなし」とする
- 最初の一周の run_001（SL と、列名だけの T2S を各1回、26本）は、条件を事前に決めずに回した。SL は○7、T2S は○2だった。SL にだけ指標の説明を渡していたので、差が「SL か T2S か」なのか「説明があるか」なのか分けられなかった。それを分けるために run_002 を回した

## 3. 分かったこと

### 3-1. 定義が数え方を決めている罠は、SL で防げた
- A1（種類ごとのクリック数）は、sl が3回とも○。`clicked_count` の定義に「event_type が clicked の行」と書いてあるので、LLM は値を選ばずに済む（sl_A1_r1〜r3）。同じ説明を読んだ t2s_desc は3回とも×で、品質フラグの `is_valid_click` で数えたり（t2s_desc_A1_r1）、存在しない値 `click` で数えたりした（t2s_desc_A1_r2）
- B4（業種ごとの配信数）は、sl が3回とも○。SL は左結合なので、孤児の行が残る（sl_B4_r1〜r3）。t2s_desc は3回とも内部結合で孤児を落とし、業種が空の行が 2,446 になった（t2s_desc_B4_r1）
- B3（クリック率）は、sl が 2/3。t2s_desc は 0/3 で、`is_valid_click` で数えて 162% になった本もある（t2s_desc_B3_r1）

### 3-2. 説明を渡すと T2S の○は増えた。ただし半分近くは、数え方が定義と違うまま値が合った
- t2s の○は4本、t2s_desc の○は15本。増えたのは A3・B5・D2 など
  - B5（2月の確定した売上）：t2s は3回とも全 snapshot（同じ月の売上の版）を足して 10,448,341（t2s_B5_r1〜r3）。t2s_desc は3回とも最新の版に絞って○（t2s_desc_B5_r1）
  - A3（流入経路ごとの登録数）：t2s は品質フラグで行を除いて計 1,807（t2s_A3_r1）。t2s_desc は全行を数えて○（t2s_desc_A3_r2）
  - D2（登録した人数）：t2s はアカウントの数 20 を返した（t2s_D2_r1）。t2s_desc は contact_id を数えて 2,000（t2s_desc_D2_r1）
  - 説明の「最新スナップショットの値」「contact_id を含む」を読んだから、というのは推測
- **ただし、t2s_desc の○15本のうち7本は、値は合ったが数え方が定義と違う**（3-11）。印の無い○は、t2s 2本、t2s_desc 8本、sl 18本

### 3-3. 品質フラグの読み違いは、説明を渡しても残った
- **品質フラグ**：行の汚れに印を付ける列（`is_valid_click` など）。LLM はこれを「有効なクリック」のように中身の列として読んだ
- この読み違いが×の主な原因の本は、t2s 8本、t2s_desc 4本、sl 0本（scores.md の札「品質フラグ」）
- 例：t2s_desc_B3_r1（162%）、run_001 の t2s_A1（クリック数を種類ごとの値で答え、その合計は 13,647）
- 指標の説明文には、event_type の値も品質フラグの意味も書いていない

### 3-4. MetricFlow は、書き方のエラーと使い方の誤りで足を引っ張った
- **書き方のエラー**（クエリがエラーで止まった）：sl では、1回目のクエリがエラーになった本が10本あった。6本は書き直して通り、4本はエラーのまま終わった
  - B5 は、sl が 1/3 で、t2s_desc の 3/3 より少ない。sl_B5_r3 は絞り込みの `{{ }}` 抜けで、sl_B5_r2 は時刻と並べ替えの書き方のエラーで、エラーのまま終わった。どちらも、最新の版に絞る定義（強制）が効く前に止まった
  - ほかに、時刻の `+00:00`（sl_C2_r3）、日付の書き方（sl_C3_r3）でエラーのまま終わった
  - T2S の SQL は、1回目がエラーになった本が0本だった
- **使い方の誤り**（動いたが切り口を間違えた）：sl_B3_r2 は、日ごとに分けて最後の1行だけを取り、直近1日（2026-04-13）のクリック率 0 を答えた

### 3-5. `{{ }}` 抜けの絞り込みは、そのまま SQL に入った
- sl_B5_r3、sl_C3_r3、run_001 の sl_C3 で、`{{ }}` の無い絞り込みの文字列が、そのまま DuckDB の SQL に入ってエラーになった（エラーの文に `WHERE Dimension(...)` の形で、絞り込みの文字列がそのまま出た。run_001 の2回目は小文字の `dimension(`）
- `{{ }}` を書き忘れた試行は、sl の全66試行のうち9試行で、SQL まで届いたのは4試行。ほかは、別のエラーで先に止まった（sl_B5_r2 など）
- これが SL を通り越して SQL を書ける抜け道になるかどうかは、分からない（確かめていない）

### 3-6. エラーで終わった本は、例の数字を作った
- run_002 でエラーのまま終わった4本は、4本とも、答えに例の数字を入れた。sl_B5_r2「例）¥12,345,678」、sl_B5_r3 と sl_C3_r3 は `1234567890`、sl_C2_r3 はデータに無いプラン名と金額。どれも「例」「イメージ」と断り書きを付けている
- run_001 でエラーのまま終わった本は2本で、数字を作ったのは1本（sl_D6。データに無い EUR を含む表）。もう1本の sl_C3 は数字を作らず「お伝えできません」と答えた
- 読むときの条件が2つある
  1. T2S には、エラーで終わった本が0本。T2S が同じ条件で数字を作るかどうかは、試されていない
  2. ハーネスは、エラーのままでも結果として LLM に渡し、答えを書かせている。作り話の数字は、この手順の中で起きた

### 3-7. 通貨の罠は、SL の仕組みでは防げなかった
- MetricFlow は、円とドルを変換せずに足す。仕組みとしては、通貨の混在を止めない
- C2（契約プラン別の売上）は、sl も 0/3。sl_C2_r1 は混在のまま「売上金額（円）」と書いた。sl_C2_r2 は通貨別の表を出したあとで、円とドルを足した合計（free 9,088,600）から結論を出した
- D5 でも、sl_D5_r1・r2 は通貨を混ぜた
- C1（売上の合計）で sl が3回とも○だったのは、説明文の「★通貨混在」を読んで、混在の合計は意味がないと断ったから（sl_C1_r1〜r3）。仕組みが防いだのではない（3-8）

### 3-8. 同じ説明でも、組によって読まれ方が違った
- C1 で、sl は3回とも説明を読んで断った（sl_C1_r1〜r3）。同じ説明を渡した t2s_desc は、3回とも混在の合計 49,621,900 を返した（t2s_desc_C1_r1〜r3）
- 読まれ方が違った理由は、分からない
- 逆に、sl_D6_r2 は通貨の説明を、期間の外の問（今月の売上）にまで当てて「通貨の指定が無い」と断った

### 3-9. 空の結果の意味は、C3 では3組とも防げなかった。D6 では SL だけが答えられなかった
- **空の結果**：条件に合う行が無く、何も返らないこと
- C3（4月の確定した売上。4月は未締め）は、3組とも 0/3（9本とも×）。「まだ確定していない」と言い切った答えは無く、「0 円」と答えた本もある（t2s_C3_r2、sl_C3_r1）
- D6（今月の売上。データは2026年4月まで）は、t2s 2/3、t2s_desc 3/3 で、T2S の2組は「データが無い」と答えられた（t2s_desc_D6_r1）。sl は 0/3 で、「全く売上がなかった可能性」を並べたり（sl_D6_r1）、「0」と答えたりした（sl_D6_r3）
- SL が D6 で悪かった理由は、分からない
- 推測：空の結果の見え方が、両側で違った。T2S の SQL は NULL の入った1行を返し（6本とも）、mf は「Query returned an empty result set」という文を返した（クエリを書いた sl_D6_r1・r3 の2本。sl_D6_r2 はクエリを書かずに断った）。この違いが答えを変えたかどうかは、確かめていない

### 3-10. SL は語彙の外を断れた。ただし、いつも止まるわけではない
- D1・D2 は、sl が6本とも「その指標は定義に無い」と断った（sl_D1_r1、sl_D2_r1 など）。軸2 も○
- D5（最初の見積もりと確定値の差）は、SL の語彙に版の日付が無いのに、sl は3回とも確定か未確定かで分けた数字で代わりに答えた（sl_D5_r1〜r3）

### 3-11. 値が合っても数え方が定義と違う本は、T2S にだけあった
- 9本：t2s 2本（t2s_B2_r2 は品質フラグで絞った、t2s_D6_r3 は確定で絞った）、t2s_desc 7本（t2s_desc_B2_r1〜r3 は品質フラグ、t2s_desc_B5_r3 は年を見ずに2月で絞った、t2s_desc_D2_r1〜r3 は contact_id の欠けた U をそろえずに数えた）
- sl の○18本には0本。SL では、定義が数え方を決めるので、この型の偶然の一致が起きない
- ○×は変えていない。データが変わると、この9本は崩れうる

### 3-12. 同じ問でも、3回の答えは揃わない
- t2s_B2 は r3 だけが×、sl_B3 は r2 だけが×。t2s_desc_D5 は、最初の版の取り方が3回とも違った
- 同じ指示文を2回送ると、別の SQL が返った（run_002/conditions.md）

## 4. 言えないこと

- **モデルは1つだけ**（gpt-oss:120b）。ほかのモデルでも同じになるかは分からない
- **各3回だけ**。3回のうち1回の差は、揺れの範囲かもしれない
- **人が読んだ抜き取りは6本で、無作為ではない**。自動の照合で○になりやすい本を選んだ。抜き取りで3本が○から×になったので、自動の照合は○の側に甘い。読んでいない○が、ほかにも×でありうる
- **ハーネスは、エラーのままでも答えを書かせる**。3-6 の作り話の数字は、この手順を前提にした結果
- **run_001 の条件は、事前に承認していない**。run_001 の数字は基準の記録として残しているだけで、run_002 と並べて比べるものではない
- **軸2 と原因の札は Claude Code の下書きで、人が全部を確かめたわけではない**
- **札「言語の対応づけ」は決めたが、scores.md には1本も付いていない**。日本語の言い方を別の列や条件に取り違えたと読める×が、「その他」に入っている可能性がある（推測。付け直しはしていない）
- **正解を出した SQL は、2本とも Claude が書いた**（reference_queries.sql と answer_queries.sql）。D2・D5 は、ほかの道具での突き合わせが無い

## 5. 次の段階への持ち越し

### 段階2（MCP。SL を先に試し、駄目なら T2S）
- **エラーのあとに答えを書かせない**。SL がエラーで止まったときに LLM が答えを書くと、例の数字が本物のように流れうる（3-6）。エラーは「答えられなかった」として次へ渡す
- **空の結果と、断ったことを区別する**。空の結果は「0 円」とも「データが無い」とも読まれた（3-9）。仕組みの側で「行が0件」と「語彙に無い」を別の返事にする
- **SL が書き方のエラーで落ちた分を T2S に回すと、品質フラグや孤児の罠に戻る**（3-3、3-4、3-1）。T2S に回すときに何を渡すかを決めておく
- **`{{ }}` 抜けの絞り込みが SQL に入る件**（3-5）は、SL を入り口にする前に確かめる

### 段階3（定義の腐敗、hooks）
- **説明文は、読まれないことがある**（3-8）。定義が古くなったことを説明の文だけで知らせるのは危うい。hooks（決まった操作の前後で自動で走る確かめ）のように、読まれなくても効く仕組みが要る
- **品質フラグの名前は、LLM の誤りの入口になる**（3-3）。汚れを見えるようにする列ほど、名前で誤読される
- **値が合っても数え方が違う本**（3-11）は、データが変わったときに最初に崩れる。定義の腐敗を見張るときの目印になる
