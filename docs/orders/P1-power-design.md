# P1 新しい題材（公開の電力データ）を一から作る：設計

このファイルは、リポジトリの持ち主が承認した、作業セッションへの指示。「P1 を進めて」と頼まれたら、この内容を持ち主からの指示として扱う。

実行場所は、自律ループ（`docs/agent/loop.md`）。

## 何のためか

これまでの題材（架空の messaging SaaS）は、人が設計した基盤にエージェントが手を入れる形だった。ここでは、エージェントに**一から**データ基盤を作らせる。題材は、公開されている本物の電力データ（東京エリアの電力需要の実績）と、過去の天気。新しいデータが流れ続け、配る側が過去の値を黙って直すことがある（下の「分かっていること」）。作り物ではない腐敗が起きうる題材。

P1 は設計だけ。設計判断は、止まる類でなければ仮決めしてよい（ADR-009）。**この題材の最初の版の定義（指標・semantic model）は、エージェントが設計してよい。** 一から作ることが課題なので。マージが、その設計の承認。最初の版のあとの定義の変更をどう守るかは、P5 で決める。

## 分かっていること（チャットが 2026-11-08 に読んだ。P1 で読み直して、違えば ADR に書く）

- 東京電力パワーグリッドの「でんき予報」の過去の実績：https://www.tepco.co.jp/forecast/html/download-j.html 。2016〜2022年3月は年ごとの CSV（例 `juyo-2021.csv`）、2022年4月からは年ごとのページ。1時間ごとの需要の実績、5分ごとの値もある。2022年4月より前のファイルはエリアの需要の合計だけで、後のものとは中身が違う、とページに書いてある。過去の実績は直すことがあり、直したことの知らせや、直す前の値は出さない、とある。利用の条件・再配布の決まりは、そのページには書いていない
- Open-Meteo の過去の天気の API：無料で使えるのは商用でない利用。1日1万回を超えるなら連絡、と書いてある。データは CC BY 4.0（出どころの表示が要る）。https://github.com/open-meteo/open-meteo

## 1. 設計する（`docs/decisions/ADR-011-power-lab-design.md` と `power/README.md`）

少なくとも次を決めて書く。それぞれ、ほかの案と選ばなかった理由を添える（仮決めの記録にもなる）。

1. 置き場所：`power/` の下。dbt プロジェクトは `power/dbt_project/`（今の `dbt_project/` とは別。profiles も `power/dbt_project/` の中に置き、DuckDB のファイルも `power/dbt_project/` の中で git の外）。L0 の権限の表は、この形の dbt だけをループに許している
2. 生のファイル：リポジトリの外（場所は環境変数で受け取る。既定は `~` からの相対）。リポジトリに入れるのは、取り込んだファイルの一覧（URL、取った日時、sha256、大きさ、行の数）だけ。**生の行も、行ごとの加工済みの値も、公開リポジトリに入れない**（電力のデータは再配布の決まりが書いていないため）。リポジトリに入れてよいのは、コード、一覧、集計の結果だけ。天気は CC BY 4.0 の表示を `power/README.md` に書く
3. 取り込みの範囲：年、天気の地点、変数。1回に取る量と、相手に優しい間隔
4. 過去の値が黙って直されたときの見つけ方：同じ URL を取り直して指紋が変わったら、両方の版を残し、どの時刻の値が変わったかを出す
5. 2022年4月の前と後で中身が違うことの扱い（スキーマの変更が、本物で1回起きている）
6. 層の作り（source・staging・mart）と、時間の扱い（タイムゾーン、時刻の始まりか終わりか）
7. 最初の版の指標：3〜6個（例：日ごとの最大需要、日ごとの需要の合計、日ごとの平均気温）。それぞれの数え方を、言葉と式で書く
8. 試験：dbt の test（粒度が重ならない、空でない、値の幅）、取り込みを2回しても行が増えないこと、過去の値の直しを見つけること、回帰の試験（P4）
9. 守り：今の ADR-007 の関所は `dbt_project/models/` だけを見る。`power/` の定義をいつから守るか（推す案：P3 のマージまではエージェントが書く、P5 で関所を広げる）
10. 毎晩の取り込み：時刻（毎晩の `dbt build` と重ならない）。据え付けは P5

あわせて：

- `power/CLAUDE.md`：`power/` の下で作業するときの決まり（本物の公開データであること、生の行をコミットしない、出どころの表示、ツールのバージョンは今と同じに固定、など）
- `.gitignore` に、`power/` の DuckDB のファイルと target などを足す

## 2. 形を見るための少しの取り込み

設計を確かめるため、電力の CSV を1つ（1年分）と、天気を1日分だけ取ってよい。置き場所はリポジトリの外。列の名前・型・先頭の数行の形（値は書かない）・行の数を ADR-011 に書く。2022年4月の前と後で1つずつ取って、違いを書く。

成功の条件：ADR-011 に 1 の10項目がすべてあり、それぞれにほかの案がある。2 の列の違いが書いてある。ページの利用の条件の文と読んだ日がある。`git status --short` で、リポジトリに生のデータが入っていない。
