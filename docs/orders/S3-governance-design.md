# S3 段階3のまとめの文書

このファイルは、リポジトリの持ち主が承認した、作業セッションへの指示。「S3 を進めて」と頼まれたら、この内容を持ち主からの指示として扱う。

実行場所は、自律ループ（`docs/agent/loop.md`）。

## 何のためか

段階3（定義の腐敗）で、腐らせる → 見つける → 直す → 確かめる、の一巡をした。その記録は、`docs/analysis/stage3/` の下、ADR-007、決定メモ、回帰の試験（R1・G1）に散らばっている。これを1つの文書 `docs/analysis/governance-design.md` にまとめる。読む人は、このリポジトリを初めて見る人。

## 0. 始める前に

1. `main` から作業ブランチ `auto/S3` を作る
2. 読む：`docs/analysis/stage3/log.md`、`find_001/`・`find_002/` の `conditions.md` と `classes.md`、`guard_cases.md`、`guard_live.md`、ADR-007、`docs/business/` の2つのメモ、`docs/analysis/regression/`（R1 の結果）、`docs/agent/reports/G1.md`

## 1. 書く

`docs/analysis/governance-design.md`。節は次の5つ。

1. 腐らせたもの：意味の腐敗（決めごとが変わったが定義は古いまま）。dbt test が何も捕まえなかったこと
2. 見つける：エージェントは、決定メモを置くだけでは気づかず、場所を教えると気づいた。気づいたあと、どちらを正とするかを書いていないと、エージェントが自分で決めた（数え方が何通りも出た）
3. 直す：人が決めること（数え方、新旧どちらを正とするか）と、仕組みで止めること（ADR-007 の関所）。名前で守る対象を決めていた穴と、それを中身で塞いだこと。人が便利さのために決まりを緩めたこと（R3 を ask に）
4. 確かめる：形の見張り（関所）と中身の見張り（回帰の試験）の違い。試験を古い正解で作って、外れることを先に確かめたこと
5. まだ言えないこと・残った穴（ADR-007 の H1〜H5、試験の正解を誰が書き換えてよいか）

## 書き方の決まり

- 数字は、必ず出どころのファイルを添える（例：「9回中9回（`find_001/classes.md`・`find_002/classes.md`）」）。記録に無い数字を書かない。数え直したら、数え直したコマンドと出力を報告に書く
- 推測と、記録で確かめたことを分けて書く
- 人の判断は「人が決めた（日付）」と書く。人の名前は書かない
- 長さは、本文で 3,000 字前後まで

成功の条件：本文の数字の一覧を作り、すべてに出どころがあることを示す（数えた件数を出す）。個人情報の検査が通る。
