## 何のためか

Airflow の DAG は毎晩 `dbt build` を回すが、メトリクスの値は誰も毎晩見ていない（`dbt build` が通っても、数字が変わったことには気づけない）。R1 の回帰の試験の数字の層（`run_numbers.py`）と文書の層（`check_docs.py`）を毎晩回せば、定義やデータが変わったときに、次の朝には分かる。どう回すかは設計判断なので、持ち主が決める。

## 0. 始める前に

1. `main` から作業ブランチ `auto/W1` を作る
2. 読む：`airflow/dags/`、`airflow/docker-compose.yml`、`docs/analysis/regression/README.md`、`docs/agent/loop.md`、`agent/loop/README.md`

## 1. 案を書く

`docs/analysis/regression/nightly-proposal.md` に、少なくとも次の3案を、トレードオフつきで比べる。

- A：Airflow の DAG に、`dbt build` の後の1段として足す（コンテナの中で `mf` と warehouse に届くか、届かないなら何が要るか）
- B：持ち主の機械の定時の仕組み（ループと同じ launchd）で、`dbt build` の後（JST 03:30 ごろ）に回す
- C：毎晩は回さず、ループの PR ごとに回して PR に結果を貼る

比べる軸：外れたときに誰がどう気づくか（どこに何が残るか）／`dbt build` が失敗した夜の扱い／warehouse を開く時間がぶつからないか／作る手間／Airflow のコンテナとリポジトリの関係（作業中のファイルが毎晩の build に入る、ADR-007 の H3）。

推す案があれば、理由を添えて書く。**決めない。**

成功の条件：3案それぞれについて、上の軸がすべて埋まっている。事実の記述（コンテナの中に何があるか、など）には、確かめたコマンドと出力か、読んだファイルと行を添える。
