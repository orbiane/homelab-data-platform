# ADR-005: 品質フラグによる除外を行わず、通貨混在を意図的に残す

- Status: Accepted
- Date: 2026-08-31

## 背景

staging 層は汚れたデータを除去せず、真偽値のフラグで印を付けて全行を通している
（`is_valid_id` / `is_late_arrival` / `is_valid_event_type` など）。
除外の判断は下流に委譲するという方針だった。

セマンティックレイヤーはその「下流」にあたる。ここで除外するかどうかを決める。

同時に、`fct_revenue` には JPY と USD が混在している。
換算せずに合算すると意味のない数字になる。これをどう扱うかも決める必要がある。

## 決定

**品質フラグによる除外は行わない。全量を集計する。**

**通貨混在も解決しない。** 換算レートを持たせず、混在したまま残す。
ただし description と README に明記する。

## 理由

### 品質フラグについて

除外すると、汚れが存在するという事実がメトリクスから見えなくなる。
無効なIDを持つレコードを黙って落とせば、数字はきれいになるが、
データ品質の劣化は誰にも気づかれないまま進行する。

実際にこの方針の効果が現れている。`subscription_count` を業種別に集計すると、
`industry` が NULL の行が440件（全体の21.6%）現れる。これは
ディメンションテーブルに存在しないアカウントID、すなわち孤児レコードである。
LEFT OUTER JOIN で結合しているため落ちずに可視化された。

除外していれば、この21.6%は静かに消えていた。

汚れ率そのものを別メトリクスとして定義する方針だが、現時点では未実装。

### 通貨について

換算レートを導入すれば数字は「正しく」なる。しかしそれは、
セマンティックレイヤーの限界を隠すことになる。

## この決定が示すもの

セマンティックレイヤーは2種類の誤りに対して、まったく異なる振る舞いをした。

**スナップショットの多重計上は構造的に防げた。** ADR-004 の決定により、
フィルタが measure 定義の内側にある。セマンティックレイヤーを経由する限り、
どんなクエリもこれを迂回できない。

**通貨混在は防げなかった。** `revenue_amount` を通貨で絞らずに問い合わせると、
JPY 43,534,800 と USD 3,710,200 を単位無視で足した 47,245,000 が返る。
エラーも警告も出ない。もっともらしい数字が返る。

この差はどこから来るか。

多重計上は「どの行を選ぶか」の問題であり、集計式の中に条件として書ける。
通貨混在は「異なる単位のものを足してよいか」という意味論の問題であり、
集計式には書けない。換算レートという、定義の外部にある情報を必要とする。

**定義を固めれば安全になる、という素朴な理解への具体的な反例である。**
セマンティックレイヤーは曖昧性を排除するが、意味の誤りは排除しない。
そして排除できない種類の誤りは、排除できないことすら通知されない。

この論点は、後のガバナンス演習における中心的な検討対象とする。
