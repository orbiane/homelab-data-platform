# ADR-006: 生成データの版を sha256 で固定し、今の CSV を基準データとする

- Status: Accepted
- Date: 2026-10-28

## 背景

ADR-005 の 55 行目には、`revenue_amount` を通貨で絞らずに問い合わせると
47,245,000（JPY 43,534,800 / USD 3,710,200）が返る、と書いてある。
2026-10-23 に同じ問い合わせをすると 49,621,900 が返った。
データにもモデルにも、意図して手を入れた覚えはなかった。

調べると、値が動いたのは 10/23 ではなく 9/1 の深夜だった。

| 日時 | 出来事 | 根拠 |
|---|---|---|
| 2026-08-31 23:48, 23:57 | `revenue_amount` を問い合わせる（通貨別も） | `dbt_project/logs/metricflow.log.2026-09-01` |
| 2026-09-01 00:42 | 47,245,000 を書いた ADR-005 をコミット（`491f8a6`） | `git log -S '47,245,000'` |
| 2026-09-01 01:07 | `data_generation/output/` の CSV 4本が作り直される。古い CSV は上書きされて残っていない | ファイルの更新時刻 |
| 2026-10-23 / 10-28 | どちらも 49,621,900 | `mf query` |

### なぜ金額だけが変わったか

generator は乱数の種（seed）を固定して、何度動かしても同じ CSV ができるように作ってある。
ところが `data_generation/generators/revenue_monthly.py` の 66 行目だけは、
金額の元になる値を Python の `hash()` で作っている。

```python
66      seed = hash((account_id, month.isoformat())) % 1000
```

`hash()` は Python が辞書を速く引くための内部の番号で、
攻撃を防ぐために、起動のたびにわざと計算が変わる。
32 行目の `random.seed(45)` が固定するのは乱数だけで、`hash()` には効かない。
そのため generator を動かすたびに金額が変わる。
どの行をゼロや欠損にするかは固定された乱数で決めているので、行の並びは変わらないとみられる。

確定済みの行の金額は、この値そのものになる（97 行目 `amount = base`）。
新旧の値がすべて 100 の倍数なのはこのためである。

> 2026-10-28 訂正：上の「何度動かしても同じ CSV ができる」は、`subscription.py` と `message_event.py` には当てはまらない。
> この2本は event_id を `uuid.uuid4()` で作っている（`subscription.py` の 93・110・121・128 行目、`message_event.py` の 76 行目）。
> uuid4 は OS の乱数を使うので `random.seed` が効かず、generator を動かすたびに event_id が変わる。
> 段階3で generator を直すときは、`hash()` に加えて event_id の作り方も直す必要がある。

差の内訳は次の通り。差は特定の月やアカウントに偏らず、
全 6 か月・20 アカウントの最新スナップショット 92 行に散らばっている。

| 通貨 | ADR-005 の値 | 今の値 | 差 |
|---|---|---|---|
| JPY | 43,534,800 | 45,440,100 | +1,905,300 |
| USD | 3,710,200 | 4,181,800 | +471,600 |
| 計 | 47,245,000 | 49,621,900 | +2,376,900 |

47,245,000 は、作り直す前の CSV での正しい値だったとみられる。
ただし古い CSV が残っていないので、これは時刻とログからの推論であり、証明ではない。

なぜ 9/1 に作り直したかは確認できていない。
直前の 00:35 にエンティティ名を改名するコミット（`057c8df`）があり、
generator の出力する列名が変わったため、改名の作業の中で作り直した可能性が高い。

その他の指標（subscription_count / delivered_count / clicked_count / ctr）は、
今の値が 9/1 以前の記録と一致している。ただし一致を確かめたのは合計のレベルまでである。

## 選択肢

**基準データについて**

- **A. generator の `hash()` を今すぐ直す。** 誰がいつ動かしても同じ CSV になる。
  ただし金額がもう一度変わるだけで、5-4 の比較実験には得がない。
- **B. 実行時に `PYTHONHASHSEED` を固定する。** コードを変えずに済む。
  ただし付け忘れれば、また揺れる。
- **C. 今の CSV 4本を正として凍結する。** 値は 49,621,900 のまま使える。

**凍結の仕方について**

- **C1. CSV そのものをコミットする。** 作り直されれば `git status` にすぐ出る。
  ただし公開リポジトリの履歴に永久に残り、消すには履歴の書き換えが要る（CLAUDE.md で禁止している）。
- **C2. sha256 の一覧だけをコミットし、CSV の複製はリポジトリの外に置く。**
  作り直されれば指紋が合わなくなるので気づける。リポジトリは軽いままである。

**ADR-005 の数字について**

- 47,245,000 を今の値に書き換える。
- 書き換えずに注記を足し、経緯は新しい ADR に書く。

## 決定

1. **5-4 以降の基準データは、今の CSV 4本とする（C）。**
2. **CSV そのものはコミットしない。sha256 の一覧だけを `data_generation/output.sha256` としてリポジトリに入れる（C2）。**
   CSV の複製はリポジトリの外の `~/homelab-snapshots/2026-10-28/` に置く。
3. **generator の `hash()` は今は直さない（A は見送り）。PYTHONHASHSEED で固定する案（B）は採らない。**
4. **ADR-005 の 47,245,000 は書き換えない。** すぐ下に注記を足し、経緯はこの ADR-006 に書く。

## 理由

- A を今やると、5-4 の基準がもう一度動くだけである。直す作業そのものは、
  5-7 で「修正のサイクル」の演習として、数字の変化を追いながら行う方が価値がある。
- B は「毎回忘れずに付ける」という人の注意に頼る。忘れたときに何も警告が出ない点で、
  今回の事故と同じ形の失敗を残す。
- C1 は、取り返しのつかない操作（公開履歴への永久記録）を伴う。C2 なら同じ検知力を、取り返しのつく形で得られる。
- ADR は「その時点で何を判断したか」の記録である。数字を上書きすると、
  ドキュメントの数字が黙って古くなっていたという今回の事例そのものが消える。

## 基準値

データの版：`data_generation/output.sha256` に一致する CSV 4本。

| 指標 | 基準値 |
|---|---|
| revenue_amount | 49,621,900（JPY 45,440,100 / USD 4,181,800） |
| subscription_count | 2035 |
| delivered_count | 8428 |
| clicked_count | 1131 |
| ctr | 0.134196 |

### データの版の照合方法

数値を出す前や比較実験の前に、リポジトリのルートから次を実行する。

```bash
cd data_generation/output && shasum -a 256 -c ../output.sha256
```

4本とも `OK` なら基準データのままである。1本でも `FAILED` なら、CSV が作り直されている。
その場合は数値を出さずに止め、`~/homelab-snapshots/2026-10-28/` から戻すかどうかを人間が決める。

## 帰結

### 残る懸念

- **合計は一致するが、行の中身まで同じかは確かめられない。** 古い CSV が残っていないため、
  他の指標も「合計のレベルでは動いていない」までしか言えない。
- **同じ日付のスナップショットが来たときに、どれを「最新」とするかが決まっていない。**
  `dbt_project/models/staging/stg_revenue_monthly.sql` の 23〜26 行目は
  `order by snapshot_date desc` だけで並べており、同点のときの決め方がない。
  今は同点が 0 件なので害はないが、同じ日付の行が入るとビルドのたびに選ばれる行が変わりうる。
- **CSV の複製は同じ Mac の中にしかない。** ディスクの故障には備えられていない。

### 5-7 への持ち越し

- `revenue_monthly.py` の `hash()` の修正を、修正サイクルの演習として扱う。
  直すと金額が変わるので、基準値の更新と sha256 の更新までを一連の作業として追う。
- 「ドキュメントの数字が 7 週間あまり黙って古いままだった」事例として扱う。
  改名という安全そうな作業がデータの作り直しを呼び、隠れていた揺れが金額を変えた。
- 上記の「同じ日付のスナップショット」の穴は、二重ロードを仕込むときに効いてくる。
