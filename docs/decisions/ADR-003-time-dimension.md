# ADR-003: セマンティックレイヤーの時間軸に dt（処理日）を採用する

- Status: Accepted
- Date: 2026-08-31

## 背景

イベント系のファクトテーブルは2つの時刻カラムを持つ。

- `dt` — バッチが処理した日。パーティションキー
- `event_timestamp` / `added_at` — イベントが実際に発生した時刻

この分離は意図的な設計で、遅延到着データ（発生から数日遅れて届くレコード）を
仕込んであるため、両者は一致しない。

MetricFlow は semantic_model ごとに集計の基準となる時間軸を1つ要求する。
どちらを選ぶかで、メトリクスの意味が変わる。

## 選択肢

**A. event_timestamp / added_at を採用する。**
「8月1日の配信数」が文字通り8月1日に発生した配信を指す。ビジネス的に自然。

**B. dt を採用する。**
「8月1日の配信数」は8月1日のバッチが処理した分を指す。バッチ処理単位と一致する。

## 決定

**B を採用する。** `defaults.agg_time_dimension` に `dt` を指定。

## 理由

A を選ぶと、遅延到着データが届くたびに過去の数字が変わる。昨日確認した
「7月31日の配信数」が、今日見ると増えている。これは数字の信頼性に対する
直接的な脅威である。会議で使った資料の数字が後から変わることになる。

B は確定した数字が動かない。集計対象が「処理済みの範囲」として明確に定義され、
再現性が担保される。運用の一貫性を、意味の直感性より優先した。

## 帰結

- 遅延到着したレコードは、発生日ではなく処理日に計上される。
  発生日ベースで見れば当該日の数字は実態より少なく見える。
- `event_timestamp` は dimension として公開していない。必要になれば追加できるが、
  2つの時間軸を同時に公開すると利用者が混乱するため、現時点では意図的に隠している。
- 再処理・バックフィルの演習では、この選択が直接効いてくる。
  同じ `dt` を再処理したときに結果が同一になること（冪等性）が前提条件になる。
