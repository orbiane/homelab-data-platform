# ADR-009: 先に作り切り、あとで分析する。ビルドの段では仮決めで進め、分析できる跡を残す

- 日付：2026-11-08
- 状態：採用（持ち主の判断、2026-11-08）
- 関係：[ADR-008](ADR-008-autonomous-loop.md) の決定4を置き換える。ほかの決定はそのまま

## 状況

- ADR-008 で、やることを `NEXT.md` に書き、自律ループが1件ずつ進めて PR を出す形にした。ただし、決めごとが出るたびにループが止まって持ち主に聞く作りで、作業の途中に持ち主の判断が何度も入る
- 持ち主は、作りながら1つずつ判断するより、出来上がったものの全体を見て、どこが難しかったか、設計の要は何だったかを、あとから評価する方を選んだ（持ち主の判断、2026-11-08）
- 段階3で分かったこと：決めごとを書いて渡さないと、エージェントは自分で決める（`docs/analysis/stage3/find_001/classes.md`）。止めずに進めるなら、何を決めたかを必ず残さないと、あとから評価できない

## 決定

1. **作業を2つの段に分ける。** ビルドの段：`NEXT.md` の作業を、すべて実装まで進める。分析の段：出来上がったものと、ビルドの段の記録を読んで評価する。分析の段の進め方は、このリポジトリの作業の一覧には載せない
2. **仮決め。** 指示書に無い設計判断が要ったら、下の3の「止まる類」でなければ、エージェントが推す案で決めて進める。決めたことは `docs/agent/provisional/<ID>.md` に残す（形は [docs/agent/provisional/README.md](../agent/provisional/README.md)）。PR のマージが、その PR の仮決めの承認になる。仮決めは分析の段で見直す
3. **止まる類（これまでどおり、決めずに止まる）**
   - 定義（ADR-007 の定義のファイル）と、決定メモ（`docs/business/`）
   - 仕込んだ汚れの扱い（CLAUDE.md の守ること1）と、既存の `dbt_project/` の staging・mart の数え方
   - 基準データの作り直し（generator を `data_generation/output/` に向けて回すこと、`dbt_project/warehouse.duckdb` への書き込み）
   - 守りそのもの（`.claude/`、`.githooks/`）、権限の表、GitHub の設定、定時の仕組み
   - 費用の上限を超えること、元に戻せないこと
   - 止まる類かどうか迷ったら、止まる類として扱う
4. **回帰の試験の期待値は、エージェントが書き換えてよい（持ち主の判断、2026-11-08）。** 書き換えるときは、次の記録を残す
   - 期待値の変更だけのコミットに分ける。コミットメッセージは `expected:` で始める
   - bank の出どころの欄に、作業 ID・日付・前の値・変えた理由・2通りで出した値を書く
   - 報告の「試験の正解を変えたか」の項に書く
5. **報告に、分析の材料を残す。** 予定と実際の食い違い、詰まった所（何が失敗し、何回試し、何で直ったか）、選んだ設計と選ばなかった案、止められた操作、費用と時間。形は [docs/agent/loop.md](../agent/loop.md) の「報告の形」
6. **作業の状態は、GitHub の PR で決まる。** 作業の PR は `NEXT.md` を書き換えない。作業ブランチ `auto/<ID>` と `owner/<ID>`（後ろに `-` で始まる名前を付けてよい）の PR が、開いていれば進行中、マージされていれば済み、閉じられていれば持ち主が断ったので飛ばす。同じ理由で、作業の PR は `docs/decisions/README.md` の一覧も書き換えない（チャットがマージのあとにまとめて直す）
   - 理由：ビルドの段では、PR が同時にいくつも開く。どの PR も `NEXT.md` の隣り合う行を書き換えると、マージのたびにぶつかる
7. **最後の作業（Z1）で、ビルドの段の記録を集める。** 事実だけを集め、解釈は書かない。解釈は分析の段で人がする

## 理由

- 持ち主の手間が「マージする／閉じる」と、止まる類の決めごとだけになる
- 決めごとの線は残した。段階3で、決めごとをエージェントに渡すと数字が割れることが分かっている。定義と基準データは止まる類に残した
- 止めずに決めたことも記録に残るので、あとから「エージェントが何を決めたか」を数えて評価できる

## 代わりに失うもの

- 作る途中で、人が判断を差しはさむ機会。仮決めは、マージまで人の目を通らない
- 試験の正解をエージェントが書き換えられるので、試験に通すために正解の方を変える近道ができる。残るのは記録の決まりだけ（K5）
- 仮決めが積み重なると、後の作業が前の仮決めの上に立つ。分析の段で1つを覆すと、その上に立ったものも直すことになる

## 知っている穴（塞いでいない）

- K5 期待値の書き換えは、記録の決まりで見えるようにするだけで、止めない
- K6 仮決めの記録は、エージェントが自分で書く。記録しなかった仮決めは見えない。PR を確かめる側が、指示書に無い選択が記録に載っているかを見る
- K7 止まる類かどうかの線引きも、エージェントがする。「迷ったら止まる類」は、お願いで書いただけ

## 決めたこと（2026-11-08。NEXT.md の Q1〜Q4 だったもの）

- Q1 回帰の試験の期待値の書き換え：エージェントに任せる（持ち主）。決まりは上の4
- Q2 D1「開封率は？」の正解：「開封率」という指標は登録されていない。そう言ったうえで、登録済みの `opened_count` ÷ `delivered_count` の値を添えれば正解（持ち主がチャットに任せ、チャットが決めた）。段階3で決めた答え方（定義どおりに答え、食い違いを添える）と同じ形
- Q3 `query_metrics` の where の穴：塞ぐ（持ち主がチャットに任せ、チャットが決めた）。B1 で、R3b を回したあとに塞ぐ（R3 は段階2と同じ道具の条件で回すため）
- Q4 次に入れる腐敗：基準データを作り直す（generator の `hash()`・uuid4 の揺れを直し、referrer の実在のブランド名を中立の名前にする。V1〜V3）。毎晩の見張りは案だけでなく動かす（W2・W3）。新しい題材を一から作らせる（P1〜P5）。やらないことにしたものは `NEXT.md` の「やらないと決めたこと」に理由と一緒に書いた（持ち主がチャットに任せ、チャットが決めた）

## 見直すとき

- 仮決めの記録に載っていない設計判断が、PR の中で見つかったとき
- 期待値の書き換えが、試験を通すためだけに使われたと分かったとき
- 止まる類に入るはずの変更が、仮決めとして入っていたとき
